# 서비스와 데이터 경계

브라우저는 API Gateway를 호출하고, 각 서비스는 자신이 소유한 데이터만 읽고 씁니다. 서비스 간 계정 연결은 공통 계정 UUID로 하고, 별도 데이터베이스에 걸친 외래 키는 만들지 않습니다. 다른 서비스의 데이터가 필요하면 DB가 아니라 그 서비스의 API를 호출합니다.

| 도메인 | 서비스 | 데이터 책임 |
| --- | --- | --- |
| 공통 계정·소셜 로그인 | `dagong-auth` | 공통 사용자 ID, 소셜 계정 연결, 차단·탈퇴 상태 |
| 맛객·커뮤니티 | `matdagong-community-service` | 서비스 프로필·취향·배경 사진, 구독·구독 회차 이력, 태그 사전·제안, 포인트 원장, 알림함 |
| 장소·지도 | `matdagong-place-service` | 가게 기본정보, 맛객별 기록·메뉴·사진, 하트, 최근 본 장소, 임시 장소, 가게 정보 제보. 화면 개발용 샘플 장소도 함께 제공 |
| API 진입점 | `matdagong-api-gateway` | `/api/v1/**`와 `/media/**` 요청 전달. 도메인 데이터를 저장하지 않음 |

## 현재 흐름

공통 로그인은 `dagong-auth`가 처리합니다. 맛다공은 로그인 토큰의 공통 계정 UUID로 커뮤니티 API를 호출해 프로필·취향·구독 상태를 읽고, 지도와 장소 정보는 Gateway를 거쳐 장소 API에서 가져옵니다. 장소 기록·하트·최근 본 장소는 계정별로 장소 DB에 저장되어 기기 간에 공유됩니다. 화면의 예전 브라우저 저장 데이터는 계정 DB로 옮길 때만 읽습니다.

서비스 간 직접 호출은 두 가지입니다. 장소 서비스는 기록을 저장할 때 사용자의 토큰으로 커뮤니티의 `GET /api/v1/users/me/profile`을 호출해 작성자 닉네임·캐릭터를 가져오며, 요청 본문의 작성자 정보는 받지 않습니다. 커뮤니티 서비스는 화면이 보낸 장소 ID로 장소 서비스의 `GET /api/v1/places/{id}`를 호출해 본인 기록과 공개 여부를 확인한 뒤 맛집 등록 알림을 만듭니다. 알림 제목·내용·중복 방지 키는 서버가 정합니다.

직접 다녀온 곳만 근거로 남기도록, 빠른 저장(`POST /api/v1/places/drafts`)과 새 기록(`POST /api/v1/places/records`, `/records/from-like`)은 요청의 `deviceLocation`(`{ latitude, longitude }`)이 가게와 1km 안인지 장소 서비스가 다시 확인합니다(가게 좌표는 카카오 확인 값 → DB 값 → 요청 값 순). 내 기록 수정, 빠른 저장에서 이어 쓰기, 입맛에 맞았던 하트를 기록으로 바꾸기는 이미 근거가 있어 위치 없이 받습니다. 기기 위치는 결국 브라우저가 보내는 값이라 위치 조작까지는 막지 못하고, 화면을 거치지 않은 요청을 걸러 냅니다.

여러 맛객이 같은 가게를 등록하면 `restaurant_places` 한 행을 함께 씁니다. 가게 기본정보는 장소 서비스가 카카오 Local API로 같은 장소 ID를 확인했을 때만 갱신하고, 확인하지 못한 요청 값은 새 가게를 만들 때만 저장합니다.

맛객 추천은 선택 분야와 공개 취향 태그를 사용자의 비공개 선호 태그와 비교합니다. 제외 조건은 `user_preference_tags.preference_type = 'AVOID'`로 저장합니다. 이 단계는 태그 일치 기반이며 AI 분석을 전제하지 않습니다.

구독 관계와 회차별 이력은 분리되어 있습니다. 관계 테이블은 현재 구독 상태를 조회하고, 이력 테이블은 무료·유료 유형, 선택 기간, 적용 금액과 이용 기간을 회차별로 보존합니다. 무료 구독은 사용자당 활성 한 건이며 새 무료 구독을 선택하면 기존 무료 구독을 교체합니다. 유료 기간은 1·3·6·12개월입니다. 현재 결제 처리는 개발용 즉시 완료 흐름입니다.

태그 사전은 `tag_group` 하나를 분류 기준으로 사용합니다. `CUISINE`, `TASTE`, `CAFE`, `OCCASION`, `VISIT`은 각각 음식 종류, 맛·메뉴, 카페·디저트, 방문 스타일, 제외 조건을 뜻합니다. API의 `MENU`/`VISIT` 상위 분류는 그룹으로부터 계산하며 별도로 중복 저장하지 않습니다.

## 커뮤니티 DB의 주요 테이블

| 테이블 | 역할 |
| --- | --- |
| `user_profiles` | 공통 계정 UUID에 연결된 맛다공 프로필, 활동 분야·지역, 프로필 사진과 자기소개 |
| `user_profile_cover_photos` | 맛객 프로필 배경 사진(최대 10장)과 표시 순서 |
| `taste_tags` | 공개 프로필과 추천 취향에서 함께 쓰는 태그 사전 |
| `user_profile_tags` | 맛객이 공개 프로필에 선택한 태그 |
| `user_preference_tags` | 사용자가 비공개 추천 선호·제외를 위해 선택한 태그 |
| `taste_tag_requests` | 사용자가 제안한 태그·매장 이용 정보와 관리자 검토 결과 |
| `user_subscriptions` | 사용자와 맛객 사이의 현재 구독 관계 |
| `user_subscription_history` | 구독 회차별 유형·기간·금액 이력 |
| `user_point_history` | 포인트 적립·사용·조정 원장. 잔액은 거래 합계로 계산 |
| `user_notifications` | 사용자별 알림 스냅샷과 읽음 상태. 90일 보관 |
| `user_notification_settings` | 알림 종류별 받기 설정(행이 없으면 기본값) |
| `taster_reports` | 맛객 신고(이유·설명·신고한 기록의 장소). 기록에서 신고해도 올린 맛객에게 쌓고, 확인 전(PENDING) 신고는 신고한 사람·맛객마다 한 건 |
| `taster_moderations` | 신고 누적 처리 상태. 확인 전 신고 3명(불법·음란 사진은 1건)이면 `review_requested_at`(관리자 확인 목록), 5명이면 `hidden_at`(자동 가림) |

프로필의 공통 계정 UUID는 인증 DB가 소유하므로 이 DB에서 외래 키를 걸지 않습니다.

**신고로 가린 맛객**: 커뮤니티 서비스는 맛객 목록·프로필·배경 사진에서 바로 빼고, 내 프로필 응답에 `hiddenByReports: true`를 담습니다(장소 서비스는 이 값으로 새 기록·수정을 403으로 막음). 장소 서비스는 서비스 간 주소 `GET /internal/v1/hidden-tasters`(게이트웨이 경로에 없어 화면에서는 닿지 않음)를 30초마다 읽어, 본인이 아닌 사람에게 그 맛객의 기록·기록 수·공개 사진을 빼고 보여 줍니다. 그래서 가린 뒤 지도·피드에서 빠지기까지 최대 30초쯤 걸립니다. 운영에서는 커뮤니티 서비스 포트를 밖에 열지 않아야 합니다.

## 장소 DB의 주요 테이블

| 테이블 | 역할 |
| --- | --- |
| `restaurant_places` | 지도 제공자 장소 ID로 중복을 합친 가게 기본정보 |
| `restaurant_records` | 맛객별 추천 이유와 공개 범위. 작성자 닉네임·캐릭터는 저장 시점의 커뮤니티 프로필 값 |
| `restaurant_record_menus` | 기록의 추천 메뉴·가격과 선택 메뉴 사진 |
| `restaurant_record_tags` | 기록의 음식·맛 태그와 태그 그룹 |
| `restaurant_record_visit_conditions` | 직접 방문해 확인한 방문 조건 |
| `restaurant_record_photos` | 기록 사진과 표시 순서 |
| `user_place_likes` | 계정별 하트 목록. `save_origin`: LIKED(가볼 곳, 가 보고 싶어요), VISITED(다녀왔는데 입맛에 맞았어요). 다녀왔지만 별로였던 곳은 `user_place_dislikes`. 내 지도 검색으로 고른 가게는 `POST /api/v1/places/wishes`가 가게를 저장한 뒤 LIKED로 넣습니다(방문 확인 없음, 기록 없는 가게는 저장한 사람에게만 보임) |
| `user_recent_places` | 계정별 최근 본 장소. 15일, 최대 30곳 |
| `place_quick_drafts` | 기록을 나중에 쓰려고 담아 둔 장소 |
| `place_reports` | 가게 기본정보 오류·폐업 제보와 관리자 확인 상태(RECEIVED·APPLIED·REJECTED). 확인 전 같은 사람·장소·이유는 한 건 |

사용자가 실제로 등록한 장소와 맛객별 추천 기록은 장소 도메인의 데이터이며, 샘플 장소 카탈로그를 운영 데이터로 간주하지 않습니다. 하트와 최근 본 장소의 `place_id`는 샘플 장소 ID(`p-...`)도 담을 수 있어 문자열로 저장합니다.

## 탈퇴

맛다공 탈퇴는 각 서비스가 자기 데이터만 지우고, 화면이 순서대로 부릅니다: 장소 `DELETE /api/v1/places/me`(기록·하트·최근 본 장소·임시 장소·제보) → 커뮤니티 `DELETE /api/v1/users/me`(프로필·취향·배경 사진, 내가 한·받은 구독과 회차 이력, 알림·알림 설정, 포인트 내역, 태그 제안, 내가 낸 신고·나를 향한 신고와 처리 상태) → `dagong-auth` `DELETE /api/v1/matdagong/membership`(맛다공 가입을 `WITHDRAWN`으로 바꾸고, 이 계정이 맛다공 client로 받은 로그인 기록 `oauth2_authorization`을 지움. 브라우저 공개 client라 refresh token이 없어 새 토큰을 더 받을 수 없고, 이미 받은 access token은 만료(기본 30분)까지 형식상 유효하며 이 브라우저의 토큰은 화면이 로그아웃하며 지움). 셋 다 다시 불러도 괜찮아 중간에 실패하면 다시 시도합니다. 공통 계정·소셜 연결은 다른 다공 서비스가 함께 쓰므로 남기고, 다시 로그인하면 맛다공 가입 절차부터 시작합니다. 구독자들이 받은 "새 기록" 알림 문구처럼 내 계정 ID 없이 저장된 스냅샷은 90일 보관 뒤 정리됩니다.

## 변경 원칙

- 한 서비스가 다른 서비스의 DB를 직접 조회하지 않습니다.
- 구독 회차·포인트처럼 이력과 정산 근거가 되는 데이터는 덮어쓰지 않고 거래 단위로 보존합니다.
- Flyway 스크립트는 적용 후 수정·삭제하지 않고 새 버전으로 변경합니다.
- 서비스가 안정적인 ID와 API 계약으로 연결되도록 합니다.

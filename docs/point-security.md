# 포인트 보안 및 원장 설계 초안

맛다공 기획자료에는 맛객 활동 보상 포인트의 상품권 교환과 향후 현금 송금 계획이 있습니다. 이 문서는 이를 현금성 가치로 취급하는 보안 기준입니다. 포인트는 일반 프로필 속성이나 클라이언트 상태로 구현하지 않고 `matdagong-point-service`가 전적으로 소유하도록 향후 구현합니다.

## 원장 모델

- 포인트 변동은 취소·수정·삭제하지 않는 append-only 거래 원장으로 기록합니다.
- 적립, 사용, 환불, 만료, 운영자 정정은 각각 구분된 거래 유형으로 저장합니다. 정정은 기존 거래를 바꾸지 않고 반대 방향 보상 거래를 추가합니다.
- 원장 항목에는 사용자 ID, 부호가 있는 정수 수량, 사유 코드, 참조 ID, 생성 시각, 멱등성 키를 둡니다.
- 잔액은 원장에서 재계산 가능한 파생값으로 취급하고, 조회 성능용 잔액 테이블을 두더라도 원장을 기준으로 정기 대사합니다.
- 포인트 서비스만 자기 DB에 쓰기 권한을 갖습니다. 구독·사용자 서비스가 포인트 DB를 직접 갱신하지 않습니다.

## 쓰기 요청 보호

- 적립량·교환 가능 여부는 서버가 정책과 검증된 이벤트를 기준으로 결정합니다. 클라이언트가 전달한 `balance`, 임의 적립량, 사용자 ID를 그대로 신뢰하지 않습니다.
- 차감은 DB 트랜잭션 안에서 잔액 확인과 원장 기록을 원자적으로 처리하고, 잔액이 부족하면 거절합니다. 동시 요청에도 중복 차감/음수 잔액이 생기지 않도록 계정 행 잠금 또는 버전 조건을 사용합니다.
- 모든 가치 변동 요청에 멱등성 키를 요구해 네트워크 재시도나 중복 클릭이 이중 적립·차감으로 이어지지 않게 합니다.
- 외부 이벤트로 지급하는 경우 이벤트 ID에 unique 제약을 두고, 실패 재처리와 원장 기록이 안전하도록 transactional outbox/inbox를 적용합니다.

## 접근 제어와 운영

- 로그인 토큰과 사용자 권한을 검증하고, 사용자는 자기 잔액/내역만 조회할 수 있게 합니다. 클라이언트에 버튼을 숨기는 것으로 권한을 대체하지 않습니다.
- 고객센터/운영자 정정은 전용 권한, 사유 입력, 감사 로그, 고액/민감 거래의 2인 승인 절차를 둡니다.
- DB 계정은 서비스별 최소 권한으로 나누고, 포인트 DB 자격증명은 저장소에 넣지 않고 배포 비밀 저장소에서 주입합니다.
- 전송 구간 TLS, 암호화된 백업, 복구 훈련, 관리자 MFA, 요청 속도 제한, 이상 적립/교환 탐지를 운영 기준에 포함합니다.
- 계좌번호와 카드정보는 포인트 서비스에 저장하지 않습니다. 현금 지급이 필요해지면 금융/지급 파트너의 토큰화 API를 검토합니다.

## 사업 전 확인할 규제 경계

포인트를 발행자 외 제휴처에서 상품·서비스를 사는 데 사용할 수 있으면 선불전자지급수단에 해당할 수 있고, 등록 또는 등록 면제 요건이 적용될 수 있습니다. 금융위원회 법령해석은 앱 활동으로 받은 포인트를 제휴사 쿠폰으로 교환하는 사례도 사용 방식에 따라 선불전자지급수단 및 선불업 등록 검토 대상이 될 수 있다고 회신했습니다. 등록 면제 기준과 세부 적용은 개별 구조 및 현행 법령에 따라 달라지므로, 상품권 교환·양도·현금 송금 중 하나라도 출시하기 전에 전자금융 규제 전문가와 금융위원회/금융감독원에 사업 구조를 확인해야 합니다. [금융위 법령해석 회신](https://better.fsc.go.kr/fsc_new/replyCase/LawreqDetail.do?lawreqIdx=5041&muGpNo=75&muNo=85&stNo=11) · [금융위 선불업 안내](https://fsc.go.kr/po010106/84178?curPage=2&srchBeginDt=&srchCtgry=6&srchEndDt=&srchKey=&srchText=)

초기 사용자 행동 검증 단계에서는 포인트를 현금 가치로 판매·충전·양도·교환하지 않고, 보상 정책 자체도 검증 뒤에 도입하는 편이 안전합니다. 이 문서는 기술 설계 메모이며 법률 의견은 아닙니다.
